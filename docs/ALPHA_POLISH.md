# Alpha 打磨记录

> **不新增功能，只优化现有交互、动画与节奏。**
>
> 直到这只灰盒狗已经让人愿意一直摸它，再开始开发喂食和拖拽。

---

## 验收标准

这一阶段没有功能清单，只有一个问题：

**你愿意一直摸它吗？**

具体拆解为三个可观察的信号：

| 信号 | 含义 |
|---|---|
| 不摸它时，它自己有事做 | 说明它是活的，而不是待机等输入 |
| 摸它时，每一下都有可感知的回应 | 说明它在回应你，而不是播放动画 |
| 看久了不觉得机械 | 说明它有节律，而不是按时钟循环 |

## 第一轮：让狗不再像时钟

### 起点：它确实是一个确定性循环

用不同随机种子跑 120 秒模拟，**行为序列完全一致**：

```
seed=1/2/3/42/999  →  Idle→Sit→Walk→Idle→Sit→Walk→...
Idle 停留 1050ms，标准差仅 71ms
9 次状态切换构成严格三轮循环
```

一只按秒表循环的动物不叫生命。而且随机种子的存在毫无意义 ——
整条决策链上没有任何随机性参与：分值是确定性函数，
阈值是常数，RNG 只用在选漫游目标点上。

### 修复链（五层，每修一层暴露下一层）

**1. 统一决策尺度（架构性缺陷）**

旧实现用 `rawScores`（纯效用）决定谁胜出，
却用 `scores`（偏好 × 效用）做门槛比较与面板展示。两者是不同的量：

```
rawScores 的领先幅度中位数  9.3
scores    的领先幅度中位数  0.056     ← 差 160 倍
```

**调试面板在说谎**：它显示 scores，但决定行为的是 rawScores。
开发者据此推断"它为什么这样动"必然得出错误结论。

修复：胜出、门槛、展示全部统一为 `scores`。

**2. 活体噪声（受性格控制）**

给候选分数加乘性噪声。关键教训：

> 噪声必须与**决策实际使用的量**同量级。

第一版只抖动门槛（±2 分），而实际余量是 9.3 分 —— 完全无效。
"加了随机数但行为完全没变"是最容易忽略的失败模式。

现改为 ±55% 权重噪声，强度由 `randomness` 维度控制 ——
于是"不可预测"成为一种性格表达，而不是散落的 `Math.random()`。

**3. 响应态豁免（曾破坏 Milestone 2）**

统一尺度后，所有互动状态变得不可达（LookAt/Approach 分数 0.15~0.29）。
根因是概念混淆：

- `stateWeights` 描述「闲来无事愿意做什么」
- 互动状态是「对玩家行为的**响应**」

用份额约束响应，就像用"你今天想散步的意愿"决定"被叫到名字该不该回头"。

修复：响应态走效用主导分（`RESPONSE_BASE_SCORE`）。

**4. 休止态折扣（Idle 是兜底，不是欲望）**

Idle 的偏好份额 0.388 本身即高于门槛 0.30 ——
意味着**从任何状态切回 Idle 都自动达标**。

后果：狗被高频拉回站立（占 61% 时间），
任何需要累积时长的行为都来不及完成（Sleep 永不出现）。

修复：给 Idle 打 0.45 折扣，使其成为"可退出的默认态"而非"支配态"。

**5. 候选集修正（最隐蔽，影响所有守卫）**

旧实现遍历所有 `stateWeights` 中的状态并**无条件给分**。
于是即便 `Sit→Walk` 被 `minDwellMs` / 冷却 / guard 拦下，
Walk 仍会以"偏好份额"获得 0.27 分并参选。

**所有守卫形同虚设。** 实测：设了 `minDwellMs = 900`，状态仍在 267ms 被切走。

修复：只有**存在可用迁移**的状态才能成为候选。

> 概念修正：偏好回答"如果有机会多想做"，
> 迁移回答"现在有没有机会"。两者是与的关系 ——
> 没有机会，再高的偏好也不该参选。

### 节奏打磨

| 措施 | 解决的问题 |
|---|---|
| **决策时刻随机化** | 固定间隔把所有时长钉在网格上（swift 的 Sit 恒为 1067ms，σ=0.000）。现让间隔在 [0.65, 1.35] 内随机，均值不变 |
| **patience 窗口按节奏缩放** | 绝对毫秒对敏捷犬种过长，swift 的 Sit/Sleep 在 180 秒内一次都不出现 |
| **minDwellMs** | 有些迁移分值极高（是门槛 10 倍），在第一个决策刻度就触发 —— 来源状态根本没"活过" |
| **性格乘子上下限 [0.5, 2.2]** | energy × curiosity 连乘达 3.61，使 Walk 分数达门槛 4 倍，Sit/Sleep 被饿死 |
| **update 顺序修正** | 原先是"先裁决、后推进时间"，裁决读到上一帧的 elapsedMs，所有基于停留时长的判断滞后一帧 |

决策时刻随机化刻意**不受性格控制**：
真实动物的注意力节律本就不等距，即便最训练有素的狗
也不可能每隔恰好 500ms 思考一次。把它交给性格控制，
等于允许"机械的狗"存在 —— 那不叫性格，叫 bug。

## 第二轮：步态动画

### 问题：狗走路时没有任何步态

渲染器完全忽略了 `RenderState` 中的 `legPhase` / `frameIndex` / `clipId`
（grep 确认零引用）。狗"走路"只是整体平移 ——
画面上是一个方块在滑动。

这是最损害"它是一只狗"的缺陷：

> 移动本身不产生生命感，**移动的方式**才产生。

### 修复：四足对角步

- 腿部作为独立图层，加入显示列表（在身体之前 → 视觉上在下方）
- **对角步相位**：左前腿与右后腿同相，右前腿与左后腿反相
  这是四足动物的通用特征，无需为每个犬种单独设计 ——
  差异体现在步频，而步频已由速度与 targetFps 决定
- 每条腿叠加两个动作：
  - 水平摆动（sin）—— 迈步
  - 垂直抬起（|cos|）—— 落脚
  只做水平摆动会像"蹭地"
- 近端腿亮色、远端腿暗色 —— 像素风里用亮度差表现纵深

**关键修正**：第一版把腿画在身体底边之上（腿顶被身体压住），
4px 高的腿几乎完全被 36px 的躯干遮住 —— 实测截图上几乎看不到腿。
现改为从身体底边向下延伸。

## 第三轮：微行为（它自己的小动作）

### 问题：空转时完全静止

`microBehaviors` 在 JSON 里声明、被 schema 校验、被类型定义 ——
但**从未被执行**。属于"死数据"。

### 为什么微行为是生命感的关键

一只活着的狗，静止时也不是完全静止的：抖耳、打哈欠、伸懒腰、叹气。

这些动作**没有目的**、**不受玩家影响**、**时机随机** ——
而恰恰是"没有目的"让它们显得真实。
如果每个动作都在回应玩家，那它只是一个输入输出系统。

### 设计：不进状态机

微行为**不进入 FSM**，这是刻意的：

- 状态机表达"它在做什么"（走路、坐下）—— 互斥、有后果、可观察
- 微行为表达"它顺手做的小动作"—— 叠加、无后果、瞬时

若把抖耳放进状态机，会产生大量无意义的状态迁移，
污染行为统计，也让"坐下"这类真正的状态难以追踪。

因此微行为作为**独立叠加层**存在：只修饰过程动画参数，不改 FSM 状态。

### 六个内置微行为

| id | 表现 | 典型频率 |
|---|---|---|
| `earTwitch` | 耳朵抖动幅度 ×5 | 5/min |
| `headShake` | 甩头 + 耳朵抖动 ×3.5 | 1.5/min |
| `yawn` | 闭眼 0.9 + 低头 + 身体微沉 | 2.5/min（精力低时） |
| `stretch` | 身体纵向拉伸 ×1.12 | 1.2/min（刚睡醒） |
| `sigh` | 极轻微的垂直下沉 | 2/min |
| `blink` | 独立眨眼 | 16/min |

**触发用泊松过程**而非固定间隔：
固定间隔会再次制造时钟感 —— 每 15 秒抖一次耳朵的狗，比完全不抖更假。

### 关键修正：顺序偏置

第一版实现是"顺序遍历，第一个命中就触发并 return"。
这看似"按概率独立"，实则列表首位的 `blink`（16/min）几乎每帧命中，
**永远轮不到后面的项**：

```
修复前：  blink 19 次 / headShake 2 / yawn 2 / stretch 0 / sigh 0
修复后：  blink 31 次 / headShake 3 / yawn 5 / stretch 2 / sigh 7
```

`sigh` 从 0 → 7，`stretch` 从 0 → 2（同时补上了 `justWokeUp` 标志）。

现改为两阶段：先各自独立判定，再从命中者中按权重择优。

## 第四轮：视觉细节

| 问题 | 修复 |
|---|---|
| 闭眼永远达不到"闭合"判定（实测稳定在 0.81，视觉上一直半闭） | 目标值由 0.85 改为 1.0 —— 插值是指数逼近，目标恰好等于阈值时永远达不到 |
| 像素风下"半闭"渲染成一条既不像睁也不像闭的短线 | 渲染层增加阈值吸附：≥ 0.9 直接吸附到全闭 |
| 哈欠结束后眼睛"啪"地睁开 | 微行为用 `max` 叠加而非覆盖，哈欠结束时自然回落 |

## 第五轮：抚摸语义（影响最大的一处）

### 问题：一个自然的抚摸动作被算成七次

原实现是「每累计 `minEffectiveMs`（90ms）结算一次有效抚摸」。
玩家按住 700ms 这**一个**自然动作，被结算成 **7 次抚摸**。

实测对照（同一次浏览器体验）：

```
按住 700ms 后立即抬手   → 第 1 次 0.85，第 2 次 1.00   ← 两次满级
按住 700ms 后等待 1.6s  → 10 次才到 0.66              ← 正常节奏
```

两者差异**全部来自"间隔"而非"摸的质量"**。
玩家会无意中发现"狂按比慢慢摸快得多"，行为被引导到错误方向。

### 第一次修复失败：从"太快"变成"太慢"

改成「一次会话只结算一次」后，结算仍发生在累计时长
刚越过 90ms 的那一刻 —— 此时算出的有效性只有 **0.278**，
而玩家实际按了 420ms。

实测每次抚摸的 `effective` 恒为 0.278，10 次才到 0.30 羁绊。

### 根因

> **按住的时长只有在抬手时才完全已知。**

在按住期间的任何时刻结算，用的都是不完整的时长。

### 正确模型：结算推迟到抬手

```
按下期间：只累加时长 + 让状态机即时响应（表现层无延迟）
抬手时：  用完整时长算一次有效性，发放一次羁绊
```

实测效果（浏览器，700ms 按住 / 1.5s 间隔）：

| 抚摸次数 | 羁绊 | 阶梯 | 狗的反应 |
|---|---|---|---|
| 1 | 0.22 | LookAt | 看向你 |
| 2 | 0.40 | Approach | — |
| 3 | 0.55 | Approach | 走过来 |
| 4 | 0.67 | Sit | — |
| 5 | 0.78 | WagTail | 坐到你旁边 |
| 6-7 | 0.85-0.91 | WagTail | 摇尾巴 |
| 8 | 0.96 | PetEnjoy | **闭眼** |

**每一次抚摸都推进阶梯** —— 这正是设计要求的"五次抚摸"体验。

不影响即时感：状态机在看按下的**第一帧**就会进入
LookAt / Approach，玩家看到的响应依然是立刻的。

### 连带修正

| 项 | 旧值 | 新值 | 原因 |
|---|---|---|---|
| 默认骚扰阈值 | 4 / 2600ms | **7 / 3200ms** | 语义修正后窗口内次数 = 实际抚摸次数，阈值 4 会让正常互动（1.25 次/秒）在第 5 次被误判 |
| 默认 `leaveAt` | 1.0 | **0.78** | 1.0 是不可达值（annoyance 上限即 1.0），导致狗永远不走开 |
| shy `gainPerPet` | 0.11 | **0.20** | 旧值在新语义下 10 次预热仅 0.928，差 0.002 到不了 PetEnjoy |

## 结果对照

### 状态时长分布

| 犬种 | 表现 |
|---|---|
| graybox | Walk 46% / Sit 29% / Idle 20% / Sleep 5%，σ 141~405ms |
| graybox-shy | **Sit 59%**（σ 1113ms）/ Walk 27% / Sleep 8% / Idle 6% |
| graybox-swift | **Walk 64%** / Sit 34% / Idle 3% |

三个犬种在**零代码改动**下呈现可读的性格差异：
害羞的爱坐着，敏捷的停不下来。

### 随机性

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 不同种子的行为序列 | 完全一致 | 各不相同 |
| Idle 时长标准差 | 71ms | 141~350ms |
| Sit 时长不同取值数 | 1 | 16 |
| 微行为种类 | 0（未实现） | 6 |
| 步态动画 | 无 | 四足对角步 |

### 亲近曲线

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 一次 700ms 按住 | 算作 **7 次**抚摸 | 算作 **1 次** |
| 满级所需抚摸次数 | **2 次** | 8 次 |
| 每次抚摸的阶梯推进 | 前两次直接跳满 | 逐级推进，每次可见 |

## 修掉的工具缺陷

标定工具本身也有三个失效，且都会**给出错误的结论**：

1. **门槛与引擎脱节**：`tune` 仍比较旧的 `UTILITY_THRESHOLD = 26`，
   报告"永不触发"而实际可达（或反之）。

2. **份额计算未复现 `personalityBias`**：
   报告 0.318（可达）而实测 0.291（不可达），
   差 9% 恰好跨过门槛 —— 于是"报告说没问题、狗却不动"。

3. **状态分布统计口径错误**：逐帧累加会把末尾未结束的状态
   算满整个窗口，实测把 Walk 报成 90%（真实值 46%）。
   现改为逐段统计。

> 标定工具最危险的失效模式是"看起来接上了、实际毫无作用"。
> 因此工具必须**完整复现引擎的公式**，而不是自己再算一遍。

## 校验器加固

本轮新增三项构建期检查，每一都对应一个真实发生过的 bug：

| 检查 | 拦截的问题 |
|---|---|
| `leaveAt ≤ 0.85` | 阈值不可达 → 狗永远不走开（发生过 2 次） |
| 阶梯阈值严格递增 | 某一级永远不被选中 |
| 微行为 id 白名单 | 拼错 id → 该微行为永远不会发生，而配置看起来正常 |
| 房间配色饱和度 | 十六进制手算错误 → 地板渲染成品红 |
| 行为 id 一致性 | 目录名与 JSON 内 id 不符 |
